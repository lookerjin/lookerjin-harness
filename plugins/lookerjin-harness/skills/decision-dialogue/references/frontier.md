# 问题依赖前沿

为当前决定维护最小记录：问题 / 为什么现在重要 / 前置决定 / 现有证据 / 推荐与代价 / 回答 / 状态。可直接在脑中或当前计划维护，不要求表单文件。

就绪集合 = 尚未解决且所有必需前置已回答的问题。先问能最大程度改变后续路线的问题，例如“离线是否必须支持”先于“同步冲突怎么展示”。同层互不依赖的问题可一起问；若用户回答改变目标，重新构造依赖而不是机械耗尽旧题单。

推荐应基于代码与目标，解释选择的机会成本、可逆性和约束。真实两难才提供备选，不把同一方案换名字凑数。用户可以给选项之外的答案。矛盾答案要指出具体冲突并收敛，不自行抹平。

区分产品决定、可实验的技术假设和授权。技术假设优先最小实验；权限问题沿用协作契约。用户已接受的决定只有出现新证据或目标变化才重开，并说明原因。

若所有问题互相依赖而无就绪项，先揭示循环：把可联合决定的问题成组，或用低成本探针固定一个前提。不能随机替用户决定必要取舍。

领域词汇只在同词异义影响设计时记录：用户用语、精确定义、生命周期、边界与反例；在代码、验收与对话中保持一致。领域实体必须有所有者，状态变化要有明确触发与可观察后果。
