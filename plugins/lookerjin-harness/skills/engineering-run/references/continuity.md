# 连续性与恢复

复用现有 Issue、计划、任务文件或当前会话状态。只有跨会话成本值得时才持久化，记录引用而非复制全仓资料。

检查点最少包含：目标与交付状态；当前 Track/必要 Mode；已获得的授权；最近一次验证所对应的源码/产物、配置和环境；完成/待办/阻塞 Unit；未决问题及其依赖；自己创建的实例/临时数据；下一项可执行动作。证据位置与失败现场一起保留。

恢复顺序：

1. 核对实际分支、HEAD、工作区改动和用户新增指示；摘要不能覆盖当前事实。
2. 检查残留进程/端口/数据归属，只回收自己创建的资源；不把进程消失理解为任务完成。
3. 对照变更范围与验收映射，判断哪些证据失效。只有证明依赖、配置与产物等价才能复用；单纯 SHA 变化不要求所有无关测试重跑，SHA 相同也不能掩盖未提交修改。
4. 将历史知识标上观察时间、来源、当时版本与适用范围；历史设计理由不写成当前代码事实。更新现有记录时保留有价值的替代关系，不另建知识数据库。
5. 恢复未决问题与就绪 Unit，从最近可信状态继续；关键事实冲突先验证，不重复完整调查。恢复结果应能立即执行：保留哪些结论；哪些输入改变、使哪项证据失效；当前阻塞；下一动作的目录、实际入口/命令、前提与预期观察。信息已在计划中时引用其位置，不再复制一份任务清单。没有就绪项才提出解除依赖所需的最小人工动作。

检查点中的“正在运行”只表示过去状态。恢复后分别确认未开始、仍等待、运行失败、查询失败、审查阻塞或已完成；查询失败不得写成任务失败或成功。环境故障先恢复运行前提，再验证原任务；不要因此重写产品。相同源码但配置、依赖或数据改变也可能使证据失效；对证明无关的变化保留有效结论。用原始入口检验恢复后的结果，不能只检查摘要是否齐全。

会话边界可用宿主原生恢复功能，由当前任务显式执行上述核对；不安装 hook 或后台调度器。
