# Execution Contract

此文件定义工程任务的共同证据与执行契约。Playbook 只定义自己的阶段；具体项目提供启动和验证配方。

## 目标与授权

从当前任务记录目标、范围、验收行为和已获得的授权。任务授权不会因为进入某个 Skill、长任务或“自主模式”而扩大。

在会话已经允许的范围内持续推进本地可逆工作。commit、push、PR、部署、生产操作、删除重要数据和对外沟通遵守用户与当前环境的确认规则；已有明确授权不重复询问。不要为记录失败先于修复而擅自提交。

## 事实与设计动机

- `confirmed`：可追溯的源码、原始资料或运行结果直接支持。
- `inferred`：基于证据的判断，写明推理和关键边界。
- `assumed`：为继续低风险工作采用的临时假设，注明如何证伪。
- `unknown`：现有信息不足，不能用合理故事填补。

实现能证明当前行为；设计动机需要历史、决策记录或当事人的明确说明。缺少历史不构成重写现有设计的理由。

## 验证记录

每项关键验收记录：行为 / surface（用户或调用者实际入口）/ 前提与输入 / 实际动作或命令 / 预期结果 / 观察结果与证据位置 / 状态 / 未覆盖边界。

优先保存工具产生的日志、退出码、返回内容或动作与状态记录，只保留能支持判断的必要片段并按项目约定脱敏。总结和自报不能代替原始记录；可重跑验证证明当前行为，不独自证明过去确实执行过。拿不到历史记录时明确该限制，不补写一份假想运行日志。

| 状态 | 意义 |
|---|---|
| `VERIFIED` | 在所声明入口执行了检查，观察结果支持该项验收 |
| `NOT_VERIFIED` | 检查明确失败，或未执行；原因分别写 `FAILED` 或 `NOT_RUN` |
| `INCONCLUSIVE` | 已尝试但证据不够、入口不匹配、环境异常或观察有歧义 |

`INCONCLUSIVE` 不计为通过，未执行不写通过。不同入口的结果分别记录，不能让单测绿色覆盖 UI 失败。构建、静态检查和 HTTP 200 证明各自的局部性质；关键验收需要对应行为、返回内容和可观察副作用。

同一入口验证应保持原始触发路径、相关配置、输入与观察点可比。外部依赖用替身时，明确其边界；不声称真实服务交互已验证。清理结束后证据仍应存在。

任务整体完成要求所有关键验收为 `VERIFIED`。存在失败、未执行或不确定项时交付部分结果，说明缺口；不要因为时间耗尽降低验收门槛。

## 规模与恢复

先获取最能区分候选的证据。低风险实验可直接做；影响长期结构的关键选择说明推荐方案与取舍，只有必须由用户决定时停下。

每个执行 Unit 至少明确目标、写入范围、必需上下文、验收、验证方式和报告；长任务加预算与禁止项。并行只用于相互独立且当前环境允许的工作，不共享写入状态。没有子 Agent 或多模型时顺序执行，标明独立性限制。

批量执行前先跑一个代表性 Unit，完成执行、验证和汇总，再根据失败修正任务与验证契约。权限、平台能力、登录或必要外部资源成为阻塞时停止盲目重试；普通恢复性失败按项目重试预算处理。

中断时保留已有证据，清理自己创建的运行资源，记录最近验证状态、未完成项和下一动作到项目既有状态位置。恢复时核对工作区与资源状态，失效证据重新验证。不要为此创建一整套 ledger、queue 或第二套项目事实库。
