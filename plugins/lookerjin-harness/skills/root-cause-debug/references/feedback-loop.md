# 调试反馈闭环

优先减少每轮验证假设的成本。方法属于 Debug / Execute ⇄ Verify，不给整个任务增加必经阶段；已由源码或编译器直接证明的问题可以直接修复并验证。

## 固定能命中原症状的反馈

先复用项目测试或验证配方，再考虑实际 CLI/HTTP 请求、浏览器动作、脱敏现场回放或最小运行子集。性能回归用计时/剖析/查询计划；输出分歧可比较已知版本。真人设备或账号操作更省成本时直接按 [协作契约](../../engineering-run/references/collaboration.md) 请求最小动作，不必穷尽自动化路线。

在现有证据位置记录：可复跑命令或操作 / 固定输入和环境前提 / 原症状的判据 / 观察结果 / 退出码 / 单次耗时 / 源码基线。命令至少真实跑过一次。凭证通过已有环境或登录状态提供，输出引用先脱敏。无法自动观察的环节注明观察者和条件。

判据必须区分三种结果：命中原症状、未命中、环境/观察失败。例如测试本就应拒绝非法输入时，退出 1 可能是正常拒绝，是否残留错误产物才是缺陷判据；连接失败也不能算修复成功。需要时用历史缺陷或隔离负对照证明判据确实会失败。新造的反馈脚本也需要验证，不能把自身断言写错当成产品缺陷。

## 缩短与稳定反馈

- 保留原始输入和长路径。一次只删一个输入、配置或操作，再运行同一判据；原症状消失就恢复该条件。最小场景用于定位，最终仍复跑原始场景。
- 分开启动成本与每轮动作，复用可安全复用的准备步骤；不要删关键初始化、数据或并发条件来换速度。先记录实际耗时，再决定是否值得优化反馈命令。
- 固定可控时间、随机种子、数据和实例状态。偶发问题记录尝试数、症状命中数、观察失败数及触发条件，比较相同条件下的结果；有限次数未复现不等于不存在。
- 重复次数和时间预算由风险、单次成本和信息增益决定，不固定循环 100 次。持续没有新信息时停止盲目重跑，改进观察点或请求必要现场。压力和故障注入限制在隔离实例。

## 让每个探针回答一个问题

候选原因分别写出可以证伪的预测；只收集能区分候选的信号。支持时使用断点/剖析，日志给本次唯一标记，记录所加位置与清理方式。不要全量打日志，也不要为简单错误凑固定数量的假设。

无可复跑环境时可以基于已有证据继续只读调查，但必须保留推断标签；不凭假设实施不可验证的试错修复。对确有依据的紧急缓解，单列目标、验证和未知项，不将其称为根因已修复。

## 修复与结束

在真实调用边界上保留能先失败后通过的回归用例。若复现依赖多个调用者、共享状态或完整时序，测试也必须覆盖该条件；缺少这样的边界是应报告的架构事实，不用内部 setter 或不相关单测代替。

修复后运行最小场景、原始触发路径及受影响回归。比较前后相同判据，说明不同环境或输入造成的比较限制。清理本次探针和临时实例，但保留失败现场与复验记录；沿用 [Verification Run](../../verification-run/SKILL.md) 的证据状态，不另建一套验收数据库。
