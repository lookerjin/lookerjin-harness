# 配方维护

维护的是项目验证能力，属于交付流程，不是 Harness 私有演化。

1. 找到唯一权威配方、完整覆盖图和上次成功同步基线；先原样运行能执行的既有检查，保存失效现场。没有基线时建立清单并标明未知，不猜测历史覆盖。
2. 比较从基线到当前的源码、配置、入口、数据流和调用者变化。追踪移动/删除的入口、新增状态写入者、错误路径和用户可见行为；不能只改失效的命令和选择器。
3. 对每个承诺核对代码与真实行为，修正映射、启动/驱动/观察/清理步骤；新入口增加必要验证，已删除行为以实际目标为准退役，不能为通过而静默降低承诺。
4. 逐项执行完整声明覆盖面；不可运行部分给出原因与最小解除动作。实际产品 bug 返回工程任务处理，维护记录与 bug 可以同时存在。
5. 输出 in-sync / updated / bug-found / blocked，可组合 updated + bug-found。只有完整覆盖核对与运行完成才推进 last-successful-sync 基线；blocked、未覆盖或产品失败保留原成功基线，并记录本次尝试。

配方声明的覆盖范围有限，不能把“覆盖图全部检查”说成整个产品无遗漏。模型维护同样检查新增写入者、假设和代码映射，见 [形式化检查](formal-checks.md)。
